01 / Problem

Government downtime should not become citizen data loss.

CivicFlow is an offline-first reliability layer, a "shock absorber", that sits between citizens and fragile government portals. It encrypts work-in-progress on the device, then syncs it automatically when the network comes back.

See the sync loop → View SDK integration

The problem

Legacy portals assume perfect internet.

  • Citizens spend 30–45 minutes filling forms and uploading documents.
  • One dropped connection, session timeout, or deadline-day server crash wipes everything.
  • The citizen starts over. Support centres flood. Public trust drops.

The solution

Offline-caching middleware. No rip-and-replace.

  • Encrypt & cache on-device (Service Worker + IndexedDB + AES-GCM).
  • Auto-sync on reconnect, with idempotent retries so nothing is sent twice.
  • Adapter to existing gov APIs (REST/SOAP). The government keeps its backend.

02 / Architecture

The offline-sync loop.

Six steps from keystroke to government record. The orange nodes are the network events CivicFlow absorbs.

Data custody, in two sentences

The payload is encrypted with a device-held, non-extractable AES-GCM key before it ever touches IndexedDB, so data at rest on the citizen's device is never stored in plain text. On reconnect the Service Worker replays the queue to Express with an idempotency key, and the local copy is deleted only after MongoDB persists it and the Government API acknowledges receipt.

Browser reality check

The Background Sync API currently works only in Chromium browsers (Chrome, Edge, Opera, Samsung Internet, Chrome for Android). Safari, iOS Safari and Firefox don't support it. CivicFlow falls back to replaying the queue on the online event or when the app reopens.

Encryption protects data at rest. It does not protect against someone using an unlocked, compromised device.

    Category
    Frontline program platform

    Not fetched

    Category
    In-house gov form platforms

Why hasn't this been built?

  1. 01

    Offline tools target field staff, not citizens. ODK, CommCare and Kobo serve trained workers on managed devices.

    CivicFlow's answer: a citizen-facing PWA that needs no app-store install.

  2. 02

    Vendors sell platforms, not middleware. Adopting them means migrating forms and data.

    CivicFlow's answer: a drop-in adapter. No rip-and-replace of the government backend.

  3. 03

    Background Sync is missing on iOS Safari and Firefox. "Automatic" sync breaks for a large share of phones.

    CivicFlow's answer: replay the queue on the online event or when the app opens.

  4. 04

    OTPs and session expiry don't work offline. Government login flows expect a live connection.

    CivicFlow's answer: deferred authentication. Fill offline, then verify the OTP before final submission.

  5. 05

    Legal grey zones. Is an offline timestamp valid for a deadline? Who is liable for data on the device?

    CivicFlow's answer: cryptographic timestamps plus policy negotiation, with data encrypted and wiped after acknowledgement.

  6. 06

    Legacy APIs aren't idempotent. Blind retries create duplicate applications.

    CivicFlow's answer: an idempotency key per submission, deduplicated on the server before forwarding.

  7. 07

    B2G sales take 12–24 months. System integrators hold the contracts.

    CivicFlow's answer: B2B2G through integrators, starting with one municipal or university pilot.

Positioning

The gap isn't "offline forms". It's a citizen-facing, drop-in reliability layer that sits in front of the portals governments already run.

05 / Stack

Greenfield stack, layer by layer.

Nothing is built yet, so every layer is a deliberate choice. Each row shows the pick, what we compared it against, and why.

Table 2 — Layer-by-layer technology decisions
Layer CivicFlow pick Alternatives considered Why
Frontend Next.js React + Vite, SvelteKit Server-rendered first load for slow phones, built-in routing, and a large talent pool.
Service Worker Serwist (@serwist/next) Hand-rolled SW, raw Workbox Workbox-based, with an official Next.js plugin and a built-in BackgroundSyncQueue.
Local store IndexedDB via Dexie localStorage, RxDB / PouchDB Stores large binary data (file uploads) asynchronously. localStorage is synchronous and only holds a few MB of strings.
Sync Background Sync + queue + online fallback PowerSync, polling Sync only needs to push submissions one way, so a full two-way sync engine is overkill. The fallback covers Safari and Firefox.
Encryption Web Crypto AES-GCM CryptoJS, none Native and authenticated (detects tampering). MDN recommends it over CBC and CTR. Keys can be non-extractable.
Backend Express Fastify, NestJS Minimal, widely known, and easy to audit for on-prem government deployments.
Database MongoDB PostgreSQL (JSONB), CouchDB Each form is a different JSON shape, so documents map naturally. Supports TTL indexes for automatic deletion.
Gov-API retry queue BullMQ + Redis In-process retry Retries with backoff survive server restarts. Failed jobs land in a dead-letter queue for review.
Validation JSON Schema (Ajv) Zod The same schema renders the form, validates in the browser, and validates on the server.

Full-stack verdict

Stack A versus Stack B across four criteria
Criterion A — Next.js + Express + MongoDB B — React/Vite + Fastify + PostgreSQL
Dev speed High: one framework covers routing, SSR and the PWA plugin. High: fast builds, but you assemble routing and SSR yourself.
Schema flexibility (dynamic forms) Native: documents fit any shape of JSON form. Good: JSONB works, at the cost of extra migration discipline.
Hiring pool Very large (MERN-style skills). Large. Fastify is less common than Express.
On-prem ease Good: MongoDB Community plus Node containers. Very good: Postgres is often already approved in government IT.

Verdict: Stack A for the MVP, because document storage matches dynamic JSON-schema forms and gets us to a demo fastest. If a pilot government mandates Postgres, PostgreSQL JSONB is a valid swap, and only the persistence layer would change.

06 / Concepts

14 concepts, in plain words.

Every technical term on this page, explained without jargon.

PWA (Progressive Web App)
A website that installs and behaves like a phone app, including working offline.
Why it matters: citizens get app-like reliability from a link, with no app-store download.
Service Worker
A small background script that sits between the page and the internet and can answer requests itself.
Why it matters: it catches a failed submission and queues it instead of showing an error.
IndexedDB
A database built into every modern browser that can store large data, including files, on the device.
Why it matters: it's where the 45 minutes of work survives a dropped connection.
Background Sync API
A browser feature that runs a task once the connection returns, even if the tab has been closed.
Why it matters: it gives automatic submission on Chromium. Other browsers need our fallback.
Web Crypto / AES-GCM
The browser's built-in encryption. AES-GCM scrambles data and also detects if anyone has altered it.
Why it matters: cached citizen data is never stored on the device in plain text.
Idempotency Key
A unique ID attached to a request so the server can tell when the same request is sent twice.
Why it matters: retries never create duplicate applications.
Middleware / Adapter
Software in the middle that translates between a modern app and an old system.
Why it matters: governments keep their backend. CivicFlow converts JSON into whatever format it expects.
Data Custody
Who holds the data, where it's stored, and for how long, at every step.
Why it matters: a clear chain of custody is how a government decides whether to trust a vendor.
Workbox (Serwist)
Ready-made libraries for writing service workers: caching rules, offline pages and request queues.
Why it matters: it avoids hand-writing error-prone offline logic.
JSON Schema Forms
A form is described as a data file, and the app draws the form from it automatically.
Why it matters: new government forms launch without redeploying the app.
Deferred Auth (OTP)
Let people fill in the form offline, and ask for the one-time password only when they're back online.
Why it matters: OTP login, which needs a connection, no longer blocks offline work.
Schema Versioning
Labelling each version of a form so old and new drafts can be told apart.
Why it matters: if the form changes while a draft is offline, the citizen only fills in the new fields.
Exponential Backoff
Waiting longer after each failed retry: 1s, then 2s, 4s, 8s, and so on.
Why it matters: it avoids hammering a government server that's already struggling on deadline day.
Cryptographic Timestamp
A tamper-evident record of exactly when something was completed.
Why it matters: it proves a form was finished before the deadline, even if it synced later.

07 / Success Criteria

What "MVP done" means.

Every line below is either a number or a pass/fail check.

Technical

  • 0 bytes of form data lost in the airplane-mode demo.

  • Queued payload syncs ≤ 5s after reconnect on Chromium, and on the next app open in Safari and Firefox.

  • 100% eventual delivery against a mock gov server with a 30% failure rate and 10s latency.

  • 0 duplicate submissions after retries (idempotency keys checked on the server).

  • Payload is AES-GCM encrypted before it's written to IndexedDB, and wiped after the server acknowledges it (checked in DevTools).

  • Installable PWA: valid manifest and service worker, passes Chrome's install criteria, and the app shell loads fully offline.

Pilot

  • 1 municipal or university pilot form live (e.g. a scholarship application).

  • ≥ 50% fewer "lost my form" support tickets than the pre-pilot baseline.

  • A measurable drop in form abandonment rate vs. the baseline, reported weekly.

  • The observability dashboard shows recovered sessions and gov API uptime.

  • Deployment stays inside government infrastructure (on-prem or private cloud), aligned with India's DPDP Act.

Illustrative mock API — the SDK isn't published yet

$ npm install @civicflow/sdk

import { CivicFlow } from '@civicflow/sdk';

CivicFlow.init({
  endpoint:   'https://civicflow.municipality.gov/api',
  formId:     'scholarship-2025',
  encryption: 'aes-gcm',        // encrypted on-device before write
  storage:    'indexeddb',
  sync: {
    strategy: 'background',     // Background Sync on Chromium
    fallback: 'on-reconnect',   // Safari / Firefox
    retry:    'exponential',
  },
  onQueued: (id) => showBanner('Saved on your device. We will submit when you are back online.'),
  onSynced: (receipt) => showReceipt(receipt.referenceNo),
});

CivicFlow.wrap(document.querySelector('#application-form'));
